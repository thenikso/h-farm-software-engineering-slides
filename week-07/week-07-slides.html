Week 07 · LO4

If the code works, is it good enough?

Working today and safe to change tomorrow are different claims.

Textbook study

§24.3, pp. 710-713. Printed pages in Sommerville (2016), 10th edition, Global Edition. See the session 7 reading guide for the study question and optional selections.

Purpose

Implementation quality is evidence that another person can understand, review, and change software reliably.

Say · rehearsal script

Working behaviour is only one part of quality. Imagine that you inherit the booking code tomorrow. You need to understand its decision, check a change, and explain it to someone else. What would make that work easier?

We will judge a small engineering record. Keep a distinction between what you can inspect and what you would still need to check. [Pause for one response, then move to the excerpts.]

Explanation6 min

Coding standards

Shared constraints make review cheaper

A convention earns its place when it removes avoidable interpretation.

Beyond formatting

Standards can cover names, structure, error handling, testing expectations, and how changes are explained.

Say · rehearsal script

A shared standard removes avoidable interpretation. If everyone names errors by the decision they represent, a reviewer spends less effort guessing what happened. That is a practical benefit, not a matter of taste.

Ask what a convention enables. Choose one contribution rule when the record opens and connect it to a reviewer’s task. [Pause for a neutral naming example.]

Documentation should answer a reader’s question. A comment can explain a surprising reason; a contribution guide can state a shared expectation; a review can record an unresolved concern. Repeating a visible line adds little.

Version history

A diff shows change. Context explains intent.

Useful history helps a reviewer reconstruct the decision without inventing it.

Read selectively

Look for the relationship between the commit summary, surrounding change, and current code. A chronological list alone is not an explanation.

Use history to ask better questions. Notice that correcting an event listing and extracting a reservation rule are separate changes. A focused change makes the claim easier to inspect. [Pause before review.]

Explanation7 min

Behaviour-preserving change

Improve structure without intentionally changing observable behaviour

The claim still needs a check.

Refactoring boundary

A refactor changes internal structure to improve future work. If required behaviour changes, it is more than a refactor.

Say · rehearsal script

A refactor aims to preserve observable behaviour. We might rename an unclear function or separate responsibilities while keeping the same outcomes for the same inputs. Changing an operating rule is a different claim.

Intention still needs verification. Even a rename can break a caller if references are missed. What focused check would protect that change? [Take one answer.]

Delivery guidance · not spoken

Check

More than one refactor can be valid

Compare clarity gained, behaviour risk, scope, and evidence.

Calibrated comparison

A smaller change may be safer; a larger extraction may create a clearer boundary. Neither is automatically stronger.

Say · rehearsal script

Different bounded changes can be defensible. Let us compare the clarity each proposal gains, the behaviour it could disturb, the scope it touches, and the evidence needed to accept it.

Smaller is a reason to consider, not an automatic verdict. A larger extraction may make a real responsibility clearer; a small rename may solve the actual reading problem at lower cost. [Use two student proposals.]
