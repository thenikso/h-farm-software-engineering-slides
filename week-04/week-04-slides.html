Explanation5 min

Is the requirement useful?

Example: “Students should be able to find the right events easily.”

BehaviourWhat must happen?Unclear. Search? Filters? Suggestions?
ConditionWhen, or for whom?Missing. Any student, any time?
EvidenceHow could we check it?We can’t. “Easily” has no measure.
BoundaryWhat is still undecided?Not said. Who decides what “right” means?

Useful, not exhaustive

A requirement should support a shared understanding and a later check. It may still name an open decision.

Must say aloud
  • Four questions: what must happen, when or for whom, how could we check it, what is still undecided.
  • An undecided point is fine if you say so. Inventing it is not.
  • Example in 5 steps: E shows it, then ask each card’s question aloud, take an answer, and press E to show ours.
Watch for · if stuck
  • Students treating every unknown as a reason to stop → “Write what is supported and name what is still open.”

Anchor · if you lose the thread

Check behaviour, condition, evidence and boundary.

Say · rehearsal script

Here is a quick way to test any requirement. What must happen? Under what condition, or for whom? How could someone check it was done? And what is still undecided?

[Press E for the example, then E after each answer.] Take “Students should be able to find the right events easily.” What must happen? Unclear: search, filters, suggestions? For whom? Any student, any time. How would we check “easily”? We can’t. What is undecided? It doesn’t say, not even who decides what “right” means. So it sounds fine, but two teams could build completely different things. Check behaviour, condition, evidence and boundary.

The fourth test matters as much as the others. If something has not been decided, say so. Do not invent a rule to make the sentence look complete.

Delivery guidance · not spoken

  • Optional extra if time: ask the room for two different things two teams might build from “find the right events easily”. Cut first if behind.
  • If behind, show all four answers quickly instead of asking the room for each.

Explanation5 min

Functional

What the system must do

A student can reserve a place on an event.

Non-functional

How well, or under what limits

The result appears within 3 seconds on a mobile connection.

Quick check

“A screen reader announces whether the booking was confirmed.” Functional or non-functional?

Non-functional: it limits how the booking result is shown, not what the system does. “Functional” is acceptable too, if the student explains why.

Behaviour and quality

Quality requirements shape behaviours. “Fast” is not useful until the operation, measure, threshold and conditions are visible.

Must say aloud
  • Functional: what the system does. Non-functional: how well, or under what limits.
  • In the memo: three functional and two non-functional are enough.
Watch for · if stuck
  • Keyboard access classed as functional → “Does it add a new thing the system does, or a limit on how it does it?” Either is acceptable if explained.

Anchor · if you lose the thread

Connect the behaviour to its quality.

Say · rehearsal script

Two kinds of requirement. Functional: something the system does, like reserving a place. Non-functional: how well it does it, or under what limits, like showing the result within three seconds on a phone.

Explanation5 min

Replace the adjective

Example: “Search must be fast.”

QualityWhat matters?Speed of event search.
MeasureWhat do we observe?Time from typing a search to seeing results.
ThresholdWhat result is acceptable?9 of 10 searches within 2 seconds.
ConditionUnder what load or context?200 events listed, on a phone over campus Wi-Fi.

And say whether the number was supplied or proposed. Here: proposed by us, to agree with the sponsor.

Measurability

The measure must fit the stakeholder outcome. A convenient number can still be irrelevant.

Must say aloud
  • Quality, measure, threshold, condition.
  • If the case gives no number, you may propose one, but label it “proposed”.
  • Example in 6 steps: E shows “Search must be fast”, then ask each card’s question and press E to show ours; the last step is the source.
Watch for · if stuck
  • A number with no condition (“within 3 seconds”) → “With how many records? On which computer?”
  • An invented number presented as agreed → “Who agreed it? Label it proposed.”

Anchor · if you lose the thread

A number needs its conditions and its source.

Say · rehearsal script

[Press E for the example, then E after each answer.] “Search must be fast.” “Fast” is an adjective. To make it checkable, name the quality: search speed. Acceptance criteria

Name the requirement, then make pass or fail clear

Tests FR1 (a student can reserve a place): Given an event with 1 place left, when a student presses Reserve, then the screen shows “Confirmed” and the event shows 0 places left.

Acceptance boundary

Criteria check a named functional requirement. They do not need to describe every test or implementation detail.

Must say aloud
  • Say which requirement you are testing.
  • Given (the setup), when (the action), then (what someone can see).
  • If it could not fail, it is not a criterion.
Watch for · if stuck
  • “Then it works correctly” → “What would someone see if it did not work?”
  • A criterion testing a feature they never wrote as a requirement → “Which FR is this?”

Anchor · if you lose the thread

Make the result observable and name what it tests.

Say · rehearsal script

An acceptance criterion says how we would know a requirement was met. Start by naming the requirement. Then: given this setup, when someone does this, then we can see that.

Here: one place left, a student presses Reserve, the screen shows Confirmed and the event shows zero places. It could pass, and it could fail. “Then it works correctly” could never fail, so it checks nothing. Make the result observable and name what it tests.

  • A common Week 5 slip is testing a requirement that was never written. Mention it here and again at slide 11.
